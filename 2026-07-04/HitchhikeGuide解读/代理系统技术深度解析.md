## 第一部分：代理训练算法深度

### 1.1 STaR：自学习推理器

```
STaR完整算法
═══════════════════════════════════════════════════════════════════

核心思想：如果模型偶尔能正确解决问题，它可以从自己的成功中学习

算法步骤：

步骤1：生成（Generate）
对数据集D中的每个问题x_i，采样推理轨迹z_i ~ π_θ(·|x_i)
得到答案 ŷ_i

步骤2：过滤（Filter）
只保留ŷ_i = y*_i（正确答案）的轨迹
定义成功集合 D_pass = {(x_i, z_i, y*_i) : ŷ_i = y*_i}

步骤3：合理化（Rationalization）← 关键创新
对模型失败的问题，生成"合理化"轨迹
z_rat_i ~ π_θ(·|x_i, y*_i)（基于正确答案的推理）
这教会模型从解反向推理

步骤4：微调（Fine-tune）
在 D_pass ∪ D_rationalized 上通过SFT更新θ

步骤5：迭代（Iterate）
用改进的模型从步骤1重复

═══════════════════════════════════════════════════════════════════
```

**STaR数学公式**：

```
STaR更新规则
═══════════════════════════════════════════════════════════════════

θ_{k+1} = argmin_θ -Σ_{(x,z,y)∈D+_k} log π_θ(z,y|x)

其中D+_k = D_pass ∪ D_rationalized

收敛动态：
- 每次迭代k增加模型的解决率p_k
- p_0 = 0.3（解决30%问题）
- 合理化 + SFT后，p_1 ≈ 0.5
- 通常3-5次迭代收敛到p ≈ 0.7-0.9

═══════════════════════════════════════════════════════════════════
```

### 1.2 Reflexion：语言强化学习

```
Reflexion完整架构
═══════════════════════════════════════════════════════════════════

核心思想：RL without weight updates - 通过自然语言自我批评改进

四个组件：

1. Actor（演员）
   - LLM代理π在环境中执行动作
   - 生成动作和观察

2. Evaluator（评估器）
   - 二元信号（任务成功/失败）
   - 或标量启发式（如通过的测试用例数）

3. Self-Reflection Generator（自我反思生成器）
   - 给定失败轨迹τ_fail和环境反馈
   - 生成自然语言反思r_text

   r_text = LLM_reflect(τ_fail, feedback, task)

4. Episodic Memory（情景记忆）
   - 滑动窗口缓冲区 M = [r_1, r_2, ..., r_m]
   - 通常m ≤ 3以适应上下文

5. Retry Loop（重试循环）
   - 下次尝试时，反思注入提示：

   a_{t+1} ~ π(·|task, M, current_state)

═══════════════════════════════════════════════════════════════════
```

**Reflexion优势与局限**：

| 优势 | 局限 |
|------|------|
| 零梯度计算；适用于冻结API模型 | 限于上下文窗口；无法积累无限知识 |
| 快速迭代（秒 vs RL训练的小时） | 无法泛化到未见任务（记忆是任务特定的） |
| 可解释：人类可读的自我纠正 | 依赖模型现有识别错误的能力 |
| 与任何基础代理架构组合 | 当基础模型太弱时退化 |

**ReAct形式化定义**：

```
ReAct轨迹定义
═══════════════════════════════════════════════════════════════════

轨迹 τ = (t_1, a_1, o_1, t_2, a_2, o_2, ...)

- t_i: Thought（内部推理，不执行）
```

### 1.4 LATS：语言代理树搜索

```
LATS算法（MCTS适配LLM代理）
═══════════════════════════════════════════════════════════════════

将蒙特卡洛树搜索（MCTS）应用于LLM代理动作选择

算法步骤：

1. 选择（Selection）
   从根节点开始，使用UCB1遍历树：
   UCB(s,a) = Q̄(s,a) + c·√(ln(N(s)) / N(s,a))
   
   其中：
   - Q̄ = 子树平均奖励
   - N = 访问计数
   - c = 探索常数

2. 扩展（Expansion）
   在叶节点，通过LLM采样生成k个候选动作：
   {a_1, ..., a_k} ~ π_θ(·|s_leaf)

3. 模拟（Simulation）
   对每个候选，在环境中执行动作
   使用快速rollout策略（贪心解码）继续到终端状态或深度限制

4. 反向传播（Backpropagation）
   将终端奖励传播到所有祖先节点
   更新Q̄和N计数

5. 重复
   运行步骤1-4直到固定计算预算（如50-200次迭代）

6. 动作选择
   选择根的最常访问的子节点

═══════════════════════════════════════════════════════════════════
```

**LATS LLM特定适配**：

```
LATS LLM适配
═══════════════════════════════════════════════════════════════════

价值函数：
使用单独的LLM调用估计状态价值：
"在0-1的范围内，这个状态导致任务成功的可能性有多大？"

基于反思的剪枝：
当分支失败时，生成反思并剪除类似分支

缓存：
存储每个节点的LLM输出，避免回溯时冗余生成

深度预算：
限制树深度为10-20步（代理很少需要更多）

性能：
在WebShop（Web导航）上：LATS达到75%成功率 vs ReAct的40%
在HumanEval（代码）上：pass@1从68%提升到94%
成本：每个任务10-50×更多推理FLOPs

═══════════════════════════════════════════════════════════════════
```

### 1.5 AgentQ：代理轨迹DPO

```
AgentQ算法
═══════════════════════════════════════════════════════════════════

核心思想：将离线偏好学习（DPO）与在线代理执行桥接
从轨迹结果自动生成偏好对

流程：

1. Rollout（展开）
   使用当前策略π_θ对每个任务执行N个轨迹

2. Evaluate（评估）
   用基于执行的奖励评分每个轨迹（二元通过/失败或标量指标）

3. Pair construction（配对构造）
   对每个任务，构造偏好对：
   (τ_w, τ_l) 其中 r(τ_w) > r(τ_l)
   
   同一任务中，最高奖励的轨迹 = chosen；最低的 = rejected

4. DPO update（DPO更新）
   对轨迹级对数概率应用标准DPO损失：
   
   L_AgentQ = -log σ(β[log(π_θ(τ_w)/π_ref(τ_w)) - log(π_θ(τ_l)/π_ref(τ_l))])

5. Iterate（迭代）
   更新的π_θ在下一轮生成新的（更好的）轨迹

═══════════════════════════════════════════════════════════════════
```

**AgentQ关键设计**：

```
AgentQ关键设计选择
═══════════════════════════════════════════════════════════════════

MCTS引导的探索：
在rollout阶段使用LATS生成多样化、高质量轨迹（更好的训练数据）

步骤级DPO：
不是比较完整轨迹，而是在动作级比较 - 给定相同前缀，
哪个下一步动作导致成功？

自我对弈改进：
每次DPO迭代产生更好的策略，生成更好的轨迹，
产生更好的训练对 - 良性循环

结果：
在WebShop上，AgentQ在3次DPO迭代中实现绝对50% → 82%成功率提升

═══════════════════════════════════════════════════════════════════
```

### 1.6 Voyager：终身学习技能库

```
Voyager架构
═══════════════════════════════════════════════════════════════════

核心思想：组合技能积累 - 代理构建不断增长的可复用代码函数库

五个组件：

1. 自动课程（Automatic Curriculum）
   LLM根据代理当前技能清单提出渐进式更难任务：
   "你现在可以挖木头和制作木板。下一个挑战：制作工作台"

2. 技能生成（Skill Generation）
   对每个任务，代理编写JavaScript函数（可执行代码）来解决它：
   skill_i = LLM(task_i, environment_docs, error_feedback)

3. 验证（Verification）
   在环境中执行代码。如果成功，添加到技能库。
   如果不成功，用错误反馈迭代（最多5次重试）

4. 技能库（向量数据库）
   每个验证的技能存储：
   - 函数签名 + 文档字符串（用于检索）
   - 任务描述的嵌入（用于语义搜索）
   - 依赖项（它调用哪些其他技能）

5. 检索 + 组合
   对新任务，检索top-k最相关的技能并组合：
   solution = LLM(new_task, retrieve(skill_library, k=5))

═══════════════════════════════════════════════════════════════════
```

### 2.2 记忆操作详解

```
记忆写入决策
═══════════════════════════════════════════════════════════════════

不是每个观察都应该存储。写入决策是一个过滤问题：

Write(e) = 1[importance(e) > τ]

其中τ是阈值，importance(e)可以是：

1. 惊讶度：-log p_θ(e|context)
   - 意外事件更有信息量

2. 奖励信号：与高|r_t|相关的事件值得记住
   - 正面或负面

3. LLM自我评估：提示模型在1-10的范围内评分重要性

矛盾检测：
在写入新事实f_new前，检查与现有记忆的冲突：

Conflict(f_new, M) = ∃f∈M: Contradicts(f_new, f)

矛盾检测可通过NLI模型或提示LLM实现
冲突时，代理必须决定：覆盖、带时间戳保留两者、或标记人工审查
```

```
记忆检索策略
═══════════════════════════════════════════════════════════════════

查询构建：
检索查询q不一定是原始观察。更好的策略：

1. HyDE（假设文档嵌入）
   - 生成假设答案

score(d,q,t) = λ·sim(q,v_d) + (1-λ)·exp(-(t-t_d)/τ_decay)
```

### 2.4 记忆反思机制

```
反思机制详解
═══════════════════════════════════════════════════════════════════

反思是一种高阶记忆操作：代理读取自己的记忆并生成洞察

Reflect(M) → {i_1, i_2, ...} ⊂ M_semantic

每个洞察i_j是从多个情景记忆派生的更高层抽象

反思实践（Reflexion）：
在三次失败尝试解决编码问题后，代理反思：

1. 从情景记忆检索三个失败情节
2. 生成洞察："我一直忘记处理输入列表为空的边界情况"
3. 将此洞察存储在语义记忆中
4. 下次尝试时，检索洞察并明确检查空输入

反思在哪里？
- 从情景记忆读取
- 写入语义记忆
- 结果洞察是上下文无关的泛化
  （"总是检查空输入"），不是情节特定记录

总结：
- 输入：情景记忆（特定过去事件）
- 计算：工作记忆（上下文中的活跃推理）
- 输出：语义记忆（持久、泛化的洞察）

这反映了生物记忆巩固，情景经验在睡眠和反思期间
逐渐转化为语义知识

═══════════════════════════════════════════════════════════════════
```

### 2.5 多代理记忆

```
多代理记忆系统
═══════════════════════════════════════════════════════════════════

当多个代理协作完成共享任务时，记忆成为协调机制

共享记忆池：
代理可能共享公共记忆存储M_shared以及私有存储M_i：

context_i(t) = R(M_i, q_i) ∪ R(M_shared, q_i)

共享记忆实现隐式协调：代理A写入发现；代理B检索它而无需显式通信

黑板架构：
经典的多代理协调机制：
- 每个代理从黑板读取和写入
- 控制器监控黑板并在前置条件满足时激活代理
- 代理通过共享状态而非直接消息通信

共享知识的共识和冲突：
当多个代理写入共享记忆时，会产生冲突。解决策略：

1. 最后写入获胜：简单但丢失信息
2. 版本化记忆：维护所有写入的历史
3. 投票/共识：要求k/n个代理同意才提交
4. 置信度加权合并：f_merged = Σ w_i f_i
5. 指定权威：将记忆区域的所有权分配给特定代理

开放问题：分布式记忆一致性
多代理系统如何在并发写入、网络分区和对抗代理下维护记忆一致性？
经典分布式系统解决方案（Paxos、Raft）适用但昂贵
近似一致性（有界过时）可能对许多代理任务足够
```

### 2.6 RL训练记忆系统

```
用RL训练记忆系统
═══════════════════════════════════════════════════════════════════

记忆操作（读、写、更新、反思）可以被视为RL框架中的动作
挑战是设计激励有用记忆行为的奖励信号

奖励信号：

1. 任务奖励传播
   如果记忆检索导致正确答案，将信用归于检索动作
   稀疏但明确

2. 检索精度奖励
   r_retrieve = Relevance(d_retrieved, task)
   由学习的相关性模型估计

3. 记忆效率奖励
   惩罚不必要的写入：r_write = -λ·1[write]
   鼓励选择性存储

4. 一致性奖励
   奖励内部一致的记忆状态（无矛盾）

组合奖励：
r_mem_t = r_task_t + α·r_retrieve_t + β·r_write_t + γ·r_consistency_t

学习记住什么：
"记住什么"问题是一个元学习挑战：
代理必须学习写入策略π_write(e)以最大化未来任务性能

这很困难因为：
1. 记忆的价值只在未来揭示（延迟奖励）
2. 写入时未来查询的空间未知
3. 记忆交互：存储e的价值取决于M中还有什么

方法：
- 事后重新标记：成功情节后，追溯标记检索到的记忆为"重要"
- 元RL：跨任务分布训练写入策略
- 好奇心驱动存储：存储惊讶的观察（高预测错误）

═══════════════════════════════════════════════════════════════════
```

### 3.3 编排模式详解

```
编排模式详解
═══════════════════════════════════════════════════════════════════

模式1：ReAct循环
- Thought_t → Action_t → Observation_t → Thought_{t+1} → ...
- "Thought"步骤是草稿本 - 不向用户显示
- 框架解析模型输出以提取动作（工具名+参数）
- 最大迭代守卫防止无限循环
- 当模型输出"Final Answer"动作或停止令牌时终止

模式2：计划-执行
- 规划阶段：生成结构化计划（带依赖的子任务列表）
- 执行阶段：执行每个子任务，可能使用不同（更便宜）的模型
- 计划修订：如果步骤失败或产生意外结果，从当前状态重新规划

Plan = Planner(q)
Result = Π_{i=1}^{|Plan|} Executor(Plan[i], context_i)

对长视野任务更高效（更少LLM调用）但对意外观察适应性较差

模式3：多代理编排

四种典型模式：

a) 监督者模式
   - 中央"监督者"接收用户请求，分解并路由子任务给专家代理
   - 结果由监督者聚合

b) 点对点
   - 代理直接通信，无中央协调器
   - 每个代理可以将任何其他代理作为工具调用
   - 灵活但更难调试，容易出现循环依赖

c) 层次化（代理树）
   - 树结构，高级代理委托给中级代理，中级委托给叶子代理
   - 实现递归任务分解
   - AutoGen的嵌套聊天中使用

d) Swarm模式
   - OpenAI的Swarm库推广
   - 使用handoffs：代理可以将控制权连同完整对话上下文转移给另一个代理
   - 关键概念：
     * 代理有指令和工具
     * Handoffs是转移控制的特殊工具
     * 上下文变量是代理间传递的共享状态
     * 活跃代理根据任务需求动态变化

═══════════════════════════════════════════════════════════════════
```
