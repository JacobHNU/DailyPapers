## 一、代理训练方法 (第12章)

### 1.1 从聊天机器人到自主代理

```
传统聊天机器人 vs 自主代理
═══════════════════════════════════════════════════════════════════

传统聊天机器人 (a)
┌────────┐         ┌────────┐
│  用户   │──提示──→│  LLM   │──响应──→ 用户
└────────┘         └────────┘
单轮，即时反馈

自主代理 (b)
┌────────┐         ┌────────┐         ┌────────┐
│  用户   │──任务──→│LLM代理 │──动作──→│  工具   │
└────────┘         └────────┘         └────────┘
                         ↑                    │
                         └────观察─────────────┘
                         │
                    ┌────▼────┐
                    │  环境    │──奖励──→ 训练信号
                    └─────────┘
多轮，稀疏终端奖励

═══════════════════════════════════════════════════════════════════
```

**关键差异**：

| 特性 | 传统LLM | 自主代理 |
|------|---------|---------|
| 步骤数 | 单轮 | 10-100+工具调用 |
| 反馈来源 | 人类偏好 | 外部环境执行 |
| 动作类型 | 纯文本 | 结构化输出（JSON/代码） |
| 奖励时机 | 即时 | 稀疏终端奖励 |
| 挑战 | 质量优化 | 长期规划、错误恢复 |

### 1.2 代理轨迹缓冲区

```
代理轨迹缓冲区结构
═══════════════════════════════════════════════════════════════════

经典RL: (s, a, r, s')

LLM代理: e_t = (S_t, A_t, R_t, S_{t+1})

其中：
- S_t: 完整上下文状态
  = 系统提示 + 用户目标 + 对话历史 + 环境变量

- A_t: 代理生成的输出
  = {文本推理, JSON工具调用}

- R_t: 外部执行环境的评估信号
  = 单元测试通过/编译标志/API响应码

- S_{t+1}: 更新的上下文窗口
  = 追加工具输出或错误日志

═══════════════════════════════════════════════════════════════════
```

**具体代理轨迹示例（代码调试）**：

```
步骤1:
  S_1 = "修复utils.py中失败的测试"
  A_1 = "让我先读取文件" + read_file("utils.py")
  R_1 = 0（中间步骤）

步骤2:
  S_2 = [之前的上下文 + 文件内容]
  A_2 = "bug在第42行，off-by-one错误" + edit_file("utils.py", ...)
  R_2 = 0（中间步骤）

步骤3:
  S_3 = [之前的上下文 + 编辑确认]
  A_3 = "让我验证修复" + run_tests()
  R_3 = +1.0（所有测试通过 - 稀疏终端奖励）
```

### 1.4 STaR：自学习推理器

```
STaR算法流程
═══════════════════════════════════════════════════════════════════

步骤1：生成
对数据集D中的每个问题x_i，采样推理轨迹z_i ~ π_θ(·|x_i)
得到答案 ŷ_i

步骤2：过滤
只保留 ŷ_i = y*_i（正确答案）的轨迹
定义成功集合 D_pass = {(x_i, z_i, y*_i): ŷ_i = y*_i}

步骤3：合理化（关键创新）
对模型失败的问题，生成"合理化"轨迹
z_rat_i ~ π_θ(·|x_i, y*_i)（基于正确答案的推理）
这教会模型从解反向推理

步骤4：微调
在 D_pass ∪ D_rationalized 上通过SFT更新θ

步骤5：迭代
用改进的模型从步骤1重复

收敛动态：
- 每次迭代k增加模型的解决率p_k
- p_0 = 0.3（解决30%问题）
- 合理化 + SFT后，p_1 ≈ 0.5
- 通常3-5次迭代收敛到p ≈ 0.7-0.9

═══════════════════════════════════════════════════════════════════
```

**STaR合理化提示**：

```python
# 标准生成（步骤1）：
PROMPT = """逐步解决以下问题。
问题：商店有45个苹果。卖出了3/5。还剩多少？
让我们逐步思考："""

# 合理化提示（步骤3）：
PROMPT = """问题：商店有45个苹果。卖出了3/5。还剩多少？
答案是18。请解释如何得到这个答案："""
# 模型学会从正确答案反向推理
```

```
- 不更新模型权重
- 通过语言自我批评学习
- 反思积累形成经验库

```

## 二、代理记忆系统 (第17章)

### 2.1 为什么代理需要记忆

```
上下文窗口瓶颈
═══════════════════════════════════════════════════════════════════

LLM本质上是无状态函数：给定提示x，产生延续分布p_θ(y|x)
每次推理从零开始
上下文窗口是唯一可用信息

问题：L = 最大上下文长度（如GPT-4o: 128,000 tokens）
- 1个token ≈ 4字符
- 典型书 ≈ 500,000字 ≈ 670,000 tokens
- 多天自主代理的观察、工具输出、推理轨迹无法放入任何固定窗口

三种失败模式：
1. 灾难性上下文遗忘
   - 事件滚出上下文窗口就不可逆地丢失
   - 无法回溯10,000 tokens前的决策

2. 无法从经验学习
   - 没有情景存储，每集都是第一次
   - 成功策略无法复用，错误重复

3. 缺乏个性化
   - 用户偏好、领域事实、关系历史必须每次重建
   - 降低用户体验和效率

═══════════════════════════════════════════════════════════════════
```

### 2.3 各类记忆详解

#### 工作记忆（短期）

**定义**：代理的活跃工作空间，当前正在处理的信息

**实现方式**：
- **草稿本**：中间推理步骤写入专用缓冲区
- **CoT缓冲区**：答案令牌前生成的推理令牌序列
- **对话上下文**：上下文窗口中的近期轮次历史

**特点**：快速（零检索延迟）、易失（上下文清除即丢失）、容量受限（受L限制）

#### 情景记忆（基于经验）

**定义**：存储特定过去事件，按上下文和时间索引

**内容**：
- **过去交互**：先前对话、任务尝试及其结果的完整或摘要记录
- **成功轨迹**：高奖励动作序列，可作为少样本示例检索
- **失败案例**：记录的错误及根本原因注释

**实现**：通常实现为向量存储，使用情节摘要的嵌入

#### 语义记忆（世界知识）

**定义**：编码与特定情节解耦的一般事实和概念

**内容**：
- **事实知识**：实体、属性和关系（如"巴黎是法国首都"）
- **领域概念**：与任务领域相关的定义、分类和本体
- **知识图谱**：结构化表示G=(V,E)

**特点**：上下文无关 - 水在100°C沸腾这一事实与何时何地学习无关

#### 程序性记忆（技能）

**定义**：编码如何做事 - 已自动化的技能和动作模式

**内容**：
- **学习的工具使用模式**：哪个API调用哪个任务，如何格式化输入
- **动作序列**：多步骤程序（如"部署代码：运行测试→构建镜像→推送→更新清单"）
- **策略作为记忆**：模型权重θ本身编码程序性知识

### 2.5 基于RAG的记忆详解

```
RAG记忆系统
═══════════════════════════════════════════════════════════════════

嵌入存储和向量数据库：
- 每个文档d_i由嵌入模型φ编码：v_i = φ(d_i) ∈ R^D
- 查询类似编码：q = φ(q)
- 检索返回按相似度排序的top-k文档

检索策略：
1. 稠密检索
   - 查询和文档由神经编码器编码（如DPR, text-embedding-3-large）
   - 捕获语义相似性，但需要GPU推理

2. 稀疏检索
   - BM25或TF-IDF的令牌重叠
   - 快速、可解释、精确关键词匹配强

3. 混合检索
   - 通过倒数排名融合(RRF)组合稠密和稀疏分数
   - RRF(d,k) = Σ_{r∈rankers} 1/(k + rank_r(d))
   - k=60是平滑常数
   - 混合始终优于单独使用

4. 重排序
   - 交叉编码器重排序器f_ψ(q,d) ∈ [0,1]联合评分
   - 管道：用ANN检索k'>>k候选 → 交叉编码器重排序 → 返回top-k

═══════════════════════════════════════════════════════════════════
```

### 2.6 记忆操作

```
四种核心记忆操作
═══════════════════════════════════════════════════════════════════

操作1：写入（Write）
├── 何时写入：重要事件发生时
├── 写入什么：事件描述、结果、学到的教训
├── 写入去向：对应类型的记忆存储
└── 挑战：决定什么值得记住

操作2：读取/检索（Read/Retrieve）
├── 查询构建：从当前上下文构建检索查询
├── 相似度匹配：在向量空间中查找相关内容
├── 结果排序：按相关性排序
└── 上下文注入：将检索结果注入当前上下文

操作3：更新（Update）
├── 冲突解决：新信息与旧信息矛盾时
├── 信息整合：合并相关信息
├── 过期清理：删除过时信息
└── 重要性衰减：降低旧信息的权重

操作4：反思（Reflect）
├── 元认知操作：对记忆本身的思考
├── 模式识别：从多个事件中提取模式
├── 知识抽象：从具体事件到一般规则
└── 记忆重组：重新组织记忆结构

═══════════════════════════════════════════════════════════════════
```

### 3.2 上下文窗口管理

```
上下文预算问题
═══════════════════════════════════════════════════════════════════

问题：上下文窗口有限（如128K tokens），但信息需求可能无限

分配策略：
┌─────────────────────────────────────────────┐
│           上下文窗口分配                      │
├─────────────────────────────────────────────┤
│ 系统提示          │ 2-10%  │ 固定           │
│ 工具描述          │ 5-15%  │ 按需加载        │
│ 少样本示例        │ 10-20% │ 动态选择        │
│ 对话历史          │ 30-50% │ 滑动窗口        │
│ 检索内容          │ 20-40% │ 按需检索        │
│ 当前输入          │ 5-10%  │ 用户提供        │
└─────────────────────────────────────────────┘

压缩策略：
1. 滑动窗口：只保留最近N轮
2. 摘要压缩：用LLM总结长历史
3. 选择性保留：保留重要信息，丢弃冗余
4. 递归分解：将长上下文分解为可管理块

```

```
核心概念：
1. 资源（Resources）

   - 文件、数据库、API响应

优势：
- 标准化接口，降低集成成本
- 可组合性，工具可复用

- 可观测性，统一日志和监控
```

### 3.6 状态管理

```
代理状态类型
═══════════════════════════════════════════════════════════════════

1. 对话状态（Conversation State）
   - 当前对话历史
   - 上下文窗口内容
   - 短期，会话结束即丢失

2. 任务状态（Task State）
   - 当前任务进度
   - 中间结果
   - 子任务依赖关系
   - 中期，任务完成即归档

3. 代理状态（Agent State）
   - 代理配置和偏好
   - 工具权限和限制
   - 长期，跨会话保持

   - 记忆系统内容
   - 学习到的模式
   - 用户画像
   - 永久，需要持久化存储

状态转换：
对话状态 ─(会话结束)─→ 归档/丢弃
任务状态 ─(任务完成)─→ 归档/总结
代理状态 ─(配置更新)─→ 持久化
持久状态 ─(持续积累)─→ 持久化
```

## 四、代理环境与基准 (第20章)

### 4.1 为什么代理需要环境

```
代理环境的作用
═══════════════════════════════════════════════════════════════════

环境提供：
1. 观察空间（Observation Space）
   - 代理可以感知的信息
   - 文件内容、API响应、网页内容

2. 动作空间（Action Space）
   - 代理可以执行的操作
   - 文件编辑、API调用、代码执行

3. 奖励信号（Reward Signal）
   - 任务成功/失败的反馈
   - 单元测试结果、编译状态

4. 状态转移（State Transition）
   - 动作执行后的环境变化
   - 文件修改、数据库更新

没有环境，代理无法：
- 验证动作的正确性
- 获取真实世界的反馈
- 学习从错误中恢复
- 评估任务完成度

═══════════════════════════════════════════════════════════════════
```

```
├── 自适应：根据代理能力调整
```

```
代理训练最佳实践
═══════════════════════════════════════════════════════════════════

   - 多目标奖励需要仔细平衡

   - 避免奖励黑客

4. 课程学习
   - 从简单任务开始
   - 逐步增加难度
   - 根据能力调整
   - 保持挑战性
```
